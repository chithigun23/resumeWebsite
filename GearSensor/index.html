Gear position system

An Arduino UNO R4 WiFi reads the shift actuator sensor and the neutral switch, works out which gear the car is in, and sends that gear to the MoTeC M1 GPRP as an analog voltage. This page covers the physical layout, the firmware structure and a draft FMEA.

  • Firmware v2 compiles for the UNO R4 WiFi, with and without CAN, WiFi and Bluetooth
  • 25 desktop test groups pass (state machine, fault reasons, CAN decode, estimate, LED display, phone data)
  • Android app built and run on a phone, with demo data
  • Bench board has the LED display build. The WiFi and Bluetooth build is not uploaded yet
  • WiFi, Bluetooth and their loop timing are untested on the board
  • Not run on the car. Timing values are starting guesses
  • CAN layout and gear estimate are placeholders and switched off
  • FMEA scores are draft estimates for the team to review

Physical architecture

The M1 drives the actuator and decides when a shift ends. The Arduino sits beside it as the gear position sensor: it watches the actuator move and reports the new gear, which closes the loop.

One shift, step by step

  1. The driver pulls a paddle. The M1 energises the up or down solenoid. The manual suggests a shift time near 150 ms.
  2. The actuator moves the selector and the LPS leaves its 1.5 to 3.0 V rest band.
  3. After the LPS has stayed past a threshold for 15 ms, the Arduino counts one shift and steps along 1, N, 2, 3, 4, 5, 6. The output changes to the new gear voltage.
  4. The M1 sees the gear change and ends the shift.
  5. The Arduino waits for the LPS to return to rest and for 100 ms to pass, compares the neutral switch with the expected gear, then accepts the next shift.

From the LPS crossing a threshold to the output changing takes about 15 to 20 ms. That has to stay well inside the M1 shift time.

What the M1 expects

  • The M1 reads the gear position sensor at high speed and ends a shift as soon as the gear changes.
  • Each gear has a calibrated position and tolerance in the M1. The Arduino voltage table has to match what the M1 learned.
  • A voltage outside the M1 diagnostic limits for longer than its diagnostic delay counts as a sensor fault, and the M1 falls back to its own gear estimate from wheel and engine speed.
  • The M1 has no support for half shifts, such as finding neutral on a motorbike gearbox. The driver handles N to 1 with the clutch.

Code architecture

The Arduino sketch only reads pins, writes the DAC, draws the LED matrix and serves the phone link. All decisions and data formats live in plain C++ headers with no Arduino dependency (state machine, CAN decode, LED display, phone data), so a PC can test them.

Who is trusted for what

Neutral switchAccurate for whether the car is in neutral. It sets the gear to N and overrides the tracked gear in every running mode.
LPSReliable for when a shift happened and whether it completed. It drives every shift event. The furthest voltage of each shift is logged, so a complete shift can be defined from data.
Gear estimateFrom CAN engine speed, wheel speed and clutch. A cross-check only, off until calibrated. If the LPS shift count and the neutral switch disagree, the gear becomes not known.

Builds

  • Default build, with WiFi and Bluetooth: 110 KB of 256 KB flash, 30% RAM. Not uploaded yet.
  • Without them, with -DGPS_WIFI_ENABLED=0 -DGPS_BLE_ENABLED=0: 58 KB, 21% RAM. The LED display build, the one on the bench board.
  • CAN, with GPS_CAN_ENABLED=1, adds about 4 KB. Uses the Arduino_CAN library that ships with the R4 core.
  • Bluetooth uses the ArduinoBLE library (2.1.0), which pulled in Arduino_SpiNINA as a dependency.
  • DEBUG is on. It prints on state changes and once a second, including the furthest LPS voltage of the last shift. Set it to false for the car.

Phone display

A diagnostics view for the bench and the car. The board makes its own WiFi network and also sends the same data over Bluetooth LE. It shows what the code thinks and why, so a fault can be read without a laptop. It does not change what the board sends to the M1.

What it shows

  • The gear in a big ring (X when not known, the same symbol as the LED matrix), and the state: UNKNOWN, ARMED, SHIFTING or FAULT.
  • Gear by LPS count beside gear by CAN estimate, and whether they agree. The estimate shows even while the logic does not use it.
  • CAN status: not built in, started, frames seen but signals stale, or signals fresh.
  • A plain-language reason whenever the gear is not known or in FAULT.
  • LPS voltage on a bar with the 1.5 V and 3.0 V thresholds, neutral switch, output to the M1, last shift peak, a log of changes, and the longest gap between samples.

Ways to connect

  • WiFi page. Join GearSensor and open http://192.168.4.1. Works on any phone.
  • Android app. Built and installed from the android folder. It scans for the board and reconnects by itself.
  • Hosted web app. chithigunatilake.com/GearSensor/live/, unlisted. Web Bluetooth needs HTTPS, so the board cannot serve this one itself.
  • Demo. The Demo button plays start-up, shifts, a disagreement, a gear mismatch and both faults.

Fault reasons

CodeShown asCause in the codeRecovers when
1Gear not knownStart-up. Nothing is assumed.The neutral switch reads neutral, or the estimate agrees long enough if it is enabled.
2Gear lost: LPS and neutral switch disagreeThe LPS count says neutral, the switch says in gear, checked 100 ms after a shift.Neutral is seen.
3Gear lost: neutral switch openedNeutral left with no shift event, only when ASSUME_FIRST_WHEN_LEAVING_NEUTRAL is false.Neutral is seen.
4FAULT: LPS out of rangeLPS outside 0.2 to 4.8 V for 15 ms.The reading is sensible and neutral is seen.
5FAULT: LPS did not return to restLPS outside the 1.5 to 3.0 V rest band for over 2 s after a shift.The reading is sensible and neutral is seen.

The reason is a reporting-only code in the state machine. It was added without changing any behaviour, and the desktop tests cover each case.

Bluetooth data

Service 7a1c0001-5e6b-4b0a-9a53-67656172536e, characteristic 7a1c0002-..., read and notify, 20 bytes, little endian.

3, 4tracked gear, LED symbol (-1 is a cross)

What it costs

  • Every radio call is a round trip to the radio module, and it shares the loop with the 5 ms sampling. Requests are limited to one per 100 ms and a slow client is dropped after 40 ms.
  • The page shows the longest gap between samples. If it climbs above about 50 ms, build for the car with -DGPS_WIFI_ENABLED=0 -DGPS_BLE_ENABLED=0.
  • WiFi and Bluetooth start-up adds a few seconds at boot, while the gear is not known anyway.
  • Neither link can send anything to the board. The page is read only.

Gaps found while writing this

  • A neutral switch stuck closed is not caught. The code trusts the switch, so a valid estimate in gear cannot overrule it.
  • Version 1 read the DAC output back on A1. Version 2 dropped that, so a wrong output voltage is not detected.
  • A floating or unpowered LPS reads mid-range and passes the range check. It only shows up as a 2 second release timeout, which the phone display now explains.
  • The M1 diagnostic limits and per-gear positions have to be set from the Arduino output before any of this is meaningful.

Open items

  • CAN wiring. The transceiver is wired with TX on D10, which is the R4 CAN TX pin. D3 has no CAN function, so the receive line has to be on D13, the only header pin with CAN RX. If D3 is the transceiver standby or enable pin, the sketch does not drive it yet.
  • CAN setup. Still needs the bus bit rate and the frame layout for engine speed, wheel speed and clutch position. CAN stays off until then, because a node at the wrong bit rate can disturb the M1 bus.
  • Estimate calibration. Measure RATIO_SCALE, wheel speed units, clutch position scale and minimum speeds from a logged run, then enable it.
  • LPS. The bench reading near 1.0 V is the unpowered sensor with the car off. With the car on, check the rest reading and travel, confirm supply and output range from the Haltech spec sheet, confirm the mount, and set the thresholds from logged shifts.
  • WiFi and Bluetooth. Upload the build that has them and check both start. Read the longest gap between samples on the board and in the car. The Android app has run only with demo data, so the Bluetooth link, notifications and automatic reconnect are untested against the board.
  • M1 setup. Set the gear position diagnostic limits and delay so 0.0 V is a fault, and learn each gear voltage from the Arduino output.
  • Timing. Measure the delay from the LPS crossing to the M1 seeing the new gear, against the M1 shift time.
  • Firmware. The bench board has the LED display build, with CAN off and DEBUG on. Set DEBUG to false for the car. The current source also has WiFi, Bluetooth and the fault reasons, and is not uploaded yet.
